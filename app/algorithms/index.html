1Preparing data

Time series & sliding windows

Turn one long list of readings into thousands of small 'question → answer' examples the AI can learn from.

Think of it like this: Like learning to predict the weather by looking at many past weeks: each time you look at the last 24 hours and check what happened in the next 4 hours.

In this project: backend/ml_models/train_lstm.py and train_gbm.py (windows_for_server / build_rows)

How it works, step by step

  1. 1A server's usage is a time series: a reading every 5 minutes, one after another.
  2. 2Take a window of the last 24 hours (288 readings): this is the question.
  3. 3The next 4 hours (48 readings) is the answer the model must learn to give.
  4. 4Slide the window forward and repeat. One month of one server gives hundreds of examples; 520 servers give more than 100,000.
  5. 5Each window comes from one single server, so the model learns how one machine behaves over time.
time serieslookback = 288 readingshorizon = 48 readingstraining example

Why 24 hours of history?

A day contains a full daily cycle (busy daytime, quiet night), so the model can see the pattern it has to continue.

2Preparing data

Normalisation (scaling)

Put all servers on the same scale so big and small machines look alike to the model.

Think of it like this: Comparing exam marks out of 100 and out of 10 is confusing until you turn both into percentages.

In this project: backend/app/services/forecast_model.py → make_features()

How it works, step by step

  1. 1CPU is already a percentage, so it is divided by 100 to sit between 0 and 1.
  2. 2Memory is in KB and differs hugely between servers (2 GB vs 64 GB).
  3. 3So each server's memory is divided by its own average of the last 2 hours: 1.0 means 'normal for this server'.
  4. 4Time of day is turned into two numbers (sine and cosine), so 23:55 and 00:05 end up close together.
  5. 5After predicting, the scaling is reversed to get real CPU % and real KB again.
featurescalingper-server normalisationsine/cosine time encoding

Why not scale memory with one global maximum?

The biggest server in the data has hundreds of GB, so a normal 2 GB server would become almost zero and the model could not see its changes.

Try it: Toggle between raw and normalised memory

Raw numbers: the small server looks like a flat line next to the big one, so the model would mostly learn about big servers.

3Preparing data

Train / validation / test split

Keep some servers hidden so we can measure accuracy honestly.

Think of it like this: A teacher keeps the final exam questions secret. If students saw them while studying, their score would not show real understanding.

In this project: server_ids()[:520], [520:600], [600:] in the training scripts

How it works, step by step

  1. 1Training servers (1–520): the model learns from these.
  2. 2Validation servers (521–600): checked during training to decide when to stop and which settings work best.
  3. 3Test servers (601–1250): never used for learning or choosing settings. All accuracy numbers come from 163 of them.
  4. 4Splitting by server (not by time) means the test checks completely new machines.
training setvalidation settest setoverfitting

How do you know the model is not just memorising?

Every score is measured on servers it never saw. Memorising training servers would not help on those.

4CPU forecast

Decision trees

A flowchart of yes/no questions that ends in a prediction.

Think of it like this: Like the game '20 questions': each question splits the possibilities until you reach an answer.

In this project: inside scikit-learn's HistGradientBoostingRegressor (each tree has up to 63 leaves)

How it works, step by step

  1. 1Start at the top with all training examples.
  2. 2Try many possible questions (e.g. 'last-hour average ≤ 20%?') and pick the one that splits the examples into the most similar groups.
  3. 3Repeat inside each group to build more levels.
  4. 4Each final box (a leaf) stores a number: the typical answer for examples that end there.
  5. 5To predict, a new server simply follows the questions down to a leaf.
node / splitleaffeaturethreshold

Why are trees good for this data?

They handle clear rules and thresholds well (e.g. 'if it was busy at this time yesterday…') and are fast to train and to run.

5CPU forecast

Gradient boosting

Build many small trees one after another; each new tree fixes the mistakes the previous trees made.

Think of it like this: Like a group of students correcting an essay in turns: each one only fixes the errors still left, so the essay gets better with every pass.

In this project: backend/ml_models/train_gbm.py and forecast_model.py → cpu_tree_rows()

How it works, step by step

  1. 1Start with a very simple prediction (the average).
  2. 2Measure the error for every example (real value − prediction). These errors are called residuals.
  3. 3Train a small tree to predict the residuals.
  4. 4Add a fraction of that tree's answer (the learning rate) to the prediction.
  5. 5Repeat hundreds of times. Our CPU model uses 400 trees, learning rate 0.06.
  6. 6Our trees predict the change from the current CPU level, using clues: recent values, averages, spikes, time of day and the same time yesterday.
  7. 7Two versions are trained: one for P50 (absolute-error loss) and one for P90 (quantile loss).
residuallearning rateensembleweak learnerboosting round

What is the difference between boosting and one big tree?

One big tree can memorise noise. Many small trees, each adding a small correction, build a smoother and more accurate prediction.

6Memory forecast

Neural networks: the neuron

A neuron multiplies each input by a weight, adds them up, and passes the result through an activation function.

Think of it like this: Like deciding whether to carry an umbrella: you weigh the clues (clouds, forecast, season), add them up, and decide.

In this project: Dense layers in backend/app/services/forecast_model.py → build_model()

How it works, step by step

  1. 1Each input (e.g. CPU now) is multiplied by a weight that says how important it is (negative weights push the other way).
  2. 2The results are added together with a bias.
  3. 3An activation function (we use GELU) bends the result so the network can learn curves, not just straight lines.
  4. 4Thousands of neurons in layers form a network. Training adjusts every weight to reduce the error.
weightbiasactivation function (GELU)layerdense layer

What does 'training' change in a neural network?

Only the weights and biases. Training nudges them, little by little, so the predictions get closer to the real answers.

Try it: Play with a single neuron

7Memory forecast

Convolution (CNN / Conv1D)

Slide a small filter along the data to detect short patterns like spikes, rises and dips.

Think of it like this: Like running a magnifying glass along a line of text, looking for one particular shape of letter.

In this project: layers.Conv1D(32, 6, strides=3) in build_model()

How it works, step by step

  1. 1A filter (kernel) is a short list of weights, e.g. 6 numbers.
  2. 2Place it at the start of the series, multiply each reading by the weight under it, add up: one output value.
  3. 3Move one step (or more: we use a stride of 3) and repeat, producing a new, shorter series.
  4. 4Our layer has 32 filters, each learning to spot a different pattern. Training discovers the best filter weights.
  5. 5This also compresses 288 readings into about 95 steps, making the LSTM's job easier.
kernel / filterstridefeature mapConv1D

Why put a CNN before the LSTM?

The CNN finds short local patterns quickly and shortens the sequence; the LSTM then reads those patterns in order to understand the longer story.

8Memory forecast

LSTM (Long Short-Term Memory)

A neural network that reads a sequence step by step and keeps a memory of what matters.

Think of it like this: Like reading a story: you remember the important events and forget the small details as you go.

In this project: layers.LSTM(64) in build_model(); trained by ml_models/train_lstm.py

How it works, step by step

  1. 1At each step the LSTM gets one new input plus what it remembered so far.
  2. 2Forget gate: decides how much of the old memory to keep.
  3. 3Input gate: decides how much of the new information to write into memory.
  4. 4Output gate: decides how much of the memory to pass on as the result for this step.
  5. 5Each gate is a small neural network with a sigmoid (0 = closed, 1 = open), so the LSTM learns what to remember.
  6. 6After the last step, its summary goes to dense layers that output 48 future memory values (P50 and P90).
cell state (memory)forget / input / output gatesigmoidrecurrent network

Why an LSTM instead of a normal neural network?

A normal network sees all inputs at once with no sense of order. An LSTM reads them in time order and keeps a memory, which suits time series.

9Training

Training: loss & gradient descent

Measure how wrong the model is (the loss) and adjust the weights a little at a time to make it smaller.

Think of it like this: Walking down a hill in fog: you feel the slope under your feet and take a step downhill, again and again.

In this project: model.compile(AdamW, pinball_loss) and model.fit(…, EarlyStopping) in train_lstm.py

How it works, step by step

  1. 1Loss: one number that says how wrong the predictions are on a batch of examples.
  2. 2Gradient: the slope, i.e. which way each weight should move to reduce the loss.
  3. 3Update: move every weight a small step downhill. The step size is the learning rate.
  4. 4Repeat over all examples (one pass = one epoch). We use the AdamW optimiser, a smart version of this.
  5. 5Early stopping: after each epoch we check the validation servers and stop when they stop improving, keeping the best weights.
lossgradientlearning rateepochbatchoptimiser (AdamW)early stopping

What is early stopping and why use it?

Training stops when the validation score stops improving. Training longer would only memorise the training servers (overfitting).

Try it: Roll the ball downhill

steps: 0

Each step moves the weight a little downhill (against the slope). A small learning rate is slow; a large one can jump over the valley and bounce around.

10Training

Quantile forecasting: P50, P90 & pinball loss

Predict a range instead of one number: the most likely value (P50) and a safe upper limit (P90).

Think of it like this: When you plan a journey, you think about the usual travel time and also the 'bad traffic' time so you are not late.

In this project: pinball_loss() in forecast_model.py; loss='quantile', quantile=0.9 in train_gbm.py

How it works, step by step

  1. 1P50 (median): real usage should be above it half the time and below it half the time.
  2. 2P90: real usage should be below it about 9 times out of 10.
  3. 3Pinball loss trains these: for P90, predicting too low is punished 9× more than predicting too high, so the model learns to aim high.
  4. 4For P50 both directions are punished equally, so it lands in the middle.
  5. 5P50 feeds the expected load; P90 feeds the busy level, protecting busy servers from being shrunk.
quantilemedianP50 / P90pinball lossuncertainty

Why not just predict one number?

One number hides the risk. P90 shows how high usage could reasonably go, so we do not shrink a server that needs room for peaks.

11Decision

Rule engine & the 95th percentile

Simple, explainable rules turn the forecast into an action: keep, right-size or shut down.

Think of it like this: Like a traffic light: clear thresholds decide green, amber or red, and anyone can check why.

In this project: backend/app/services/rule_engine.py

How it works, step by step

  1. 1Expected load = the higher of the last-24-hour average and the forecast average (P50).
  2. 2Busy level = the higher of the 95th percentile of the last 24 hours and the highest P90 forecast.
  3. 3Active (keep) if expected ≥ 25% or busy ≥ 50%.
  4. 4Right-size if expected ≥ 8% or busy ≥ 20%.
  5. 5Otherwise the server is a zombie: consolidate its work and shut it down.
  6. 6The 95th percentile ignores rare one-off spikes, unlike the maximum.
thresholdpercentileexpected loadbusy levelexplainable AI

Why use rules instead of letting the AI decide directly?

Rules are transparent: every decision can be explained and checked, and the thresholds can be changed by a company without retraining.

Try it: Maximum vs 95th percentile, then try the rules

The maximum jumps to the single spike; the 95th percentile hardly moves. That is why the rule engine uses the 95th percentile for the "busy level".

12Evaluation

Measuring accuracy

Compare predictions with what really happened on servers the model never saw.

Think of it like this: Marking an exam: check each answer against the answer key and count how many are close enough.

In this project: evaluate() in backend/ml_models/train_gbm.py → model_metrics.json

How it works, step by step

  1. 1Pick 4 random moments for each of the 163 test servers (644 windows) and forecast the next 4 hours.
  2. 2MAE (mean absolute error): the average gap between prediction and reality, in CPU percentage points.
  3. 3Within ±2 points: the share of predictions closer than 2 points to reality.
  4. 4Label accuracy: how often the predicted category (active / right-size / shut down) matches the real one.
  5. 5P90 coverage: how often reality stayed under the P90 line (target 90%).
MAEtest setcoverageaccuracy

Is 97% label accuracy the whole story?

No. Many servers in the data are idle, which makes labels easier. That is why we also report the CPU error and the P90 coverage.

Common questions about the project (with answers)

Click a question to see a short answer you can explain in your own words.

What problem does your project solve?

Companies pay for every hour a cloud server runs, even when it is idle. Our system forecasts each server's CPU and memory for the next 4 hours and recommends whether to keep it, right-size it or shut it down, with an estimated saving.

What dataset did you use?

The Bitbrains GWA-T-12 'fastStorage' dataset: real logs of 1,250 virtual machines from a data centre, one reading every 5 minutes for a month (CPU %, memory KB and more).

Which algorithms did you use, and where?

Gradient-boosted decision trees forecast CPU. A CNN-LSTM neural network forecasts memory. Both output P50 and P90. A rule engine turns the forecasts into decisions. Data preparation uses sliding windows and per-server normalisation.

Why a hybrid of two models instead of one?

We tested both on the same unseen servers. For CPU the trees were more accurate (average error 1.35 vs 1.43 points); for memory the CNN-LSTM is used. So each signal gets the model that worked best.

What is an LSTM, in simple words?

A neural network that reads data in order and keeps a memory. Gates decide what to forget, what new information to store and what to output, so it can follow patterns over time.

What is gradient boosting, in simple words?

Many small decision trees built one after another. Each new tree learns to fix the errors left by the previous trees, and their answers are added up.

What clues does the CPU model use?

The current level, the last few readings, averages over 30 minutes to 24 hours, volatility, recent minimum and maximum, the time of day, which future step is being predicted, and the reading at the same time yesterday.

What do P50 and P90 mean?

P50 is the most likely value (the median). P90 is a cautious upper limit that real usage should stay below about 9 times out of 10. They are trained with pinball (quantile) loss.

Why does the model predict the change instead of the value?

Predicting the change from the current level keeps forecasts anchored to reality: an idle server is forecast to stay idle and a busy one to stay busy, unless the clues suggest otherwise.

How did you test the model? Could it be overfitting?

Servers were split into 520 for training, 80 for validation and the rest for testing. All scores come from 163 test servers the model never saw, using 644 four-hour windows, so memorising training data would not help.

What accuracy did you get?

93.4% of CPU predictions were within ±2 percentage points, the average CPU error was 1.35 points, 97.4% of servers got the right label, and 88.5% of real readings stayed under the P90 line (target 90%).

Did you compare with a simple method?

Yes. We compared with simply assuming the current level continues. For CPU it is nearly as accurate, because 5-minute CPU readings are very noisy and hard to predict. Our model adds the P90 safety limit and more accurate memory forecasts, which a simple guess cannot give.

How does the rule engine decide?

It computes the expected load (higher of 24-hour average and forecast average) and the busy level (higher of 95th percentile and P90 peak). Active if expected ≥ 25% or busy ≥ 50%; right-size if expected ≥ 8% or busy ≥ 20%; otherwise shut down.

Why the 95th percentile and not the maximum?

The maximum jumps to a single one-off spike, which could wrongly keep an idle server alive. The 95th percentile reflects how busy the server usually gets at its peaks.

How are the savings calculated?

With fixed example prices: $110 per month for each right-sized server and $146 per month for each server shut down. Real savings would depend on the cloud provider's prices.

What are the limitations?

Short-term CPU is noisy, so no model can predict it perfectly. The prices are examples. The model was trained on one data centre's data. Phase 1 works on uploaded files, not live servers yet.

What does Phase 2 add?

Python scripts act as live servers and send a reading every second to an ingest API. Readings are stored in MongoDB time-series, the AI re-forecasts every few readings, and the dashboard updates live through WebSockets.

Why these technologies?

FastAPI (fast Python API), TensorFlow/Keras for the neural network, scikit-learn for gradient boosting, Next.js + Tailwind + Recharts for the website, and MongoDB for flexible storage of logs and accounts.
