1Overview

The problem and the idea

Companies pay for every hour a cloud server runs — even when it does nothing. This project watches each server, predicts its next 4 hours, and recommends whether to keep it, shrink it or shut it down.

  • Zombie servers: switched on, costing money, doing almost no work.
  • Oversized servers: much bigger than their workload needs.
  • Three steps: Monitor → Predict → Recommend.

2Phase 1

The data

The AI learns from the Bitbrains dataset: real logs of 1,250 virtual machines in a data centre, recorded every 5 minutes for a month.

  • Each reading: timestamp, CPU usage (%), memory usage (KB).
  • Servers behave very differently — busy, light, or idle.
  • Real data makes the predictions realistic.

3Phase 1

How Phase 1 works

You upload a CSV on the website. The Python backend reads it, splits it by server, forecasts each server's next 4 hours, applies the rules and sends the results back to the dashboard.

  • Accepts normal CSVs and original Bitbrains files.
  • Uses the most recent readings of each server.
  • Needs at least 2 hours of history (24 readings).

4Phase 1

Preparing the data and training

Servers are split into 520 for training, 80 for validation and 163 kept hidden for testing. Each server's history is cut into windows: 24 hours of input and the next 4 hours as the answer to learn.

  • One server per window — the model learns how a single machine behaves.
  • Normalisation puts big and small servers on the same scale.
  • Time of day helps spot daily rhythms.

5Phase 1

Inside the AI: a hybrid of two models

Two models work as a team. Gradient-boosted trees forecast CPU using clear clues (recent averages, spikes, time of day, same time yesterday). A CNN-LSTM neural network forecasts memory.

  • CNN finds short patterns; LSTM reads them in order with memory.
  • Boosting: each new tree fixes the mistakes of the previous trees.
  • Both predict the change from now, so a quiet server stays quiet.

6Phase 1

Reading a forecast: P50 and P90

For every future step the AI gives two numbers: P50, the most likely value, and P90, a safety limit that real usage should stay below 9 times out of 10.

  • P50 is used for the expected load.
  • P90 protects against under-sizing a server.
  • Tested on servers the model never saw.

7Phase 1

From forecast to decision

The rule engine combines history and forecast into two numbers — expected load and busy level — and applies simple thresholds. The dashboard then shows each decision with estimated savings.

  • Active: expected ≥ 25% or busy ≥ 50%.
  • Right-size: expected ≥ 8% or busy ≥ 20%.
  • Otherwise: consolidate and shut down.

8Phase 1

Results

Accuracy is measured on 163 servers the model never saw, across 644 four-hour windows.

  • CPU forecasts within ±2 percentage points most of the time.
  • Servers given the right label (active / right-size / shut down).
  • The P90 line holds close to its 90% target.

9Phase 2

Phase 2: going live

In Phase 2, Python scripts act as servers and send a reading every second to an API. Readings are stored in a MongoDB time-series database, the AI re-forecasts every few readings, and the dashboard updates live through WebSockets.

  • Same AI and rules as Phase 1 — just fed live.
  • Rolling 24-hour history for each server.
  • Inject a zombie and watch the status change.

Glossary

CPU usage

How busy a server's processor is, from 0% (doing nothing) to 100% (fully loaded).

Memory usage

How much RAM a server is using (here measured in KB, shown as MB/GB).

Zombie server

A server that is switched on (and costs money) but does almost no work.

Right-sizing

Moving a lightly used workload to a smaller, cheaper machine.

Consolidation

Moving the small amount of work from idle servers onto an active one, so the idle ones can be shut down.

Time series

Measurements taken one after another over time, e.g. CPU every 5 minutes.

Sliding window

Cutting a long time series into many examples: 24 hours of input and the next 4 hours as the answer to learn.

Normalisation

Rescaling numbers to a common range so big and small servers look alike to the model.

CNN (Conv1D)

A neural-network layer that slides a small filter along the data to detect short patterns like spikes.

LSTM

Long Short-Term Memory: a neural network that reads a sequence in order and remembers what matters.

Gradient-boosted trees

Many small decision trees built one after another; each new tree corrects the mistakes of the previous ones.

Hybrid model

Using two different models together: here trees forecast CPU and the CNN-LSTM forecasts memory.

P50 forecast

The middle (most likely) prediction: real usage is above it about half the time.

P90 forecast

A cautious upper limit: real usage should stay below it about 9 times out of 10.

95th percentile

The value that 95% of readings stay below. Unlike the maximum, one short spike does not change it much.

Train / validation / test split

Servers used to learn, to tune, and (never seen) to measure honest accuracy.

MAE (mean absolute error)

The average size of the prediction error, here in CPU percentage points.
